# Week 6 Observation

## Task 1
- Tie-breaking: when two shortest paths cost the same, my table keeps the one with the lexicographically smallest first-hop name (the heap compares (cost, node, first_hop)), so the result is deterministic. A real router does not pick one: it installs all equal-cost next hops (equal-cost multipath) and spreads flows over them by hashing the packet's addresses and ports, so one flow stays in order while the load is shared.
- u's next hop for w is x, not w. The direct link u-w costs 5, but u-x-y-w costs 1+1+1 = 3, so the table holds the neighbour that starts the cheapest path, which is adjacency plus the rest of the map, not adjacency alone.
- After u-x fails, the hops for x, y, w and z all change to v (u now reaches everything through v), and only v is unchanged, because the direct link u-v (cost 2) was already its best path.

## Task 2
- Path (A2-A5). The domestic target www.korea.ac.kr never leaves campus: from the campus Wi-Fi the hops are 172.16.0.2, 192.168.98.132 (private) and then 163.152.x.x (Korea University's own block) to the end. Where traffic really does leave is visible in the other traces: hop 3 is 163.152.233.129 (the campus edge, the same /24 as my public address) and hop 4 is 175.121.235.141, the first hop outside 163.152.0.0/16. The ocean crossing is in the trace to www.cs.cmu.edu from my phone hotspot: hop 10 answers in 34-60 ms and hop 11 (1.208.148.98) in 150-170 ms, a jump of about 120 ms in one hop (it repeated on a second run); the named hops after it are Internet2 routers at sunn (Sunnyvale), sacr, salt, denv, kans and chic, so the crossing lands on the US west coast. The hostnames do not say which cable it is, so I do not name one. www.stanford.edu showed no crossing at all (33 ms): it sits behind an AWS Global Accelerator address that is answered in Korea. 1.1.1.1 reached Cloudflare's own router 141.101.82.19 at hop 12 from the campus (7-9 ms; the last hop never answered there) and answered itself at hop 18 from the hotspot (33 ms), so the replica is near Seoul in both cases; the same address is reached by different paths from each network, which is what anycast means. A `* * *` hop has two different causes: a router that forwards packets but does not send (or is rate-limited from sending) the ICMP time-exceeded reply, after which the later hops still answer (hop 2 from the hotspot); or the probes are being dropped for good, by a firewall or by the destination itself, so every hop after the last answer is silent (hops 8-30 in several of my traces).
- Reconvergence (B2, B4, B5). Each router learned the network it is not attached to (r1 learned 172.20.0.0/16 between r2 and r3, over two equal-cost paths). Taking r1's interface down converged in 2 s, which does not match the 40 s Dead interval in FRR's defaults (Hello 10 s, Dead 40 s) because the router sees its own interface go down at once and does not wait for a timer. When I left the interface up and only dropped the OSPF packets with iptables, the table changed after 39.6 s, which is the Dead interval. Coming back took 7 to 10 s, not 2: going away is learned from a local event (or a missed-Hello timer), but a link that returns is only noticed when the next Hello arrives, which can take up to 10 s, and then the adjacency has to go through ExStart to Full (about 1.5 s) before the route is installed.
- Cost change (C3). Changing a cost with nothing failing took 1.4 s: nothing has to be noticed, the router only floods a new LSA and every router runs SPF. That is about the same as the interface-down failure (2 s, within my +/- 1 s resolution) but 28 times faster than the silent failure (39.6 s), where the network first has to realise something is wrong; that waiting is the gap Task 3 lives in.

## Task 3
- I keep three dicts of about 400 entries each (about 50 KB): dist (the cost to every node), parent (each node's predecessor, chosen the way the reference does: the neighbour that gives the final cost and has the smallest (dist, name)) and table. The reference table has to be matched exactly, ties included, which is why I had to copy its tie-break rule rather than any shortest path.
- Of the 1,000 events, 632 touched a link that lies on no shortest path (down or dearer on such a link, or up or cheaper without tying or beating the current distance) and needed no work at all, 77 changed nothing, and 291 moved some distances. I repaired those locally: on average 3.5 nodes moved (median 1, maximum 79 of 400), with a Dijkstra seeded from the unaffected border for removals and a relaxation for new or cheaper links. No event forced a full SPF; I would fall back to one if a single change moved more than 100 nodes (a quarter of the area), which never happened, so the only counted SPF is the start-up one (1 against 1,001). Ties count as "matters": an equal-cost path can change which first hop the reference picks.
- R5: the harness's wall column for my router looks no better (1.16 s against 1.09 s) because it includes the harness's own check, a full SPF after every event. Timed without that check, mine took 0.037 s against 1.02 s, so on this test it is not slower, contrary to what I expected. What a router is short of is not Python's per-operation cost but CPU time during churn: a full SPF on every flap holds the CPU of every router that sees the flap and delays hellos and forwarding updates, so avoiding it is the right choice even where it would cost wall time, and the memory it needs is tiny. The price is complexity, since an incremental router is silently wrong if one case is mishandled; I tested mine against the full SPF on about 180,000 random events, and real routers often keep the simple full SPF behind a delay timer for exactly that reason.
