# Week 5 Observation

## Task 1
- /31 returns (network, network+1, None): following RFC 3021 both addresses of a /31 are hosts on a point-to-point link, so there is no room to give one to the network and one to the broadcast. /32 returns the address itself as both first and last usable, with broadcast None, because it is a single host. The textbook's "first usable = network+1, last usable = broadcast-1" would give an empty or inverted range for both.
- 10.20.30.70 matched 10.20.30.64/26 (lab-rack-2), 10.20.30.0/24 (lab-floor), 10.20.0.0/16 (eng-building) and 10.0.0.0/8 (campus), and also the default route 0.0.0.0/0, which matches everything. Longest-prefix match picked the /26 because 26 > 24 > 16 > 8 > 0; the default is the shortest, so it only wins when nothing else matches.
- For two entries with the same network and prefix length but different next hops, my table raises ValueError, because a router cannot send one packet two ways and silently keeping the first or last would hide a configuration mistake. The same next hop added twice is just ignored.

## Task 3
- I grouped the routes by prefix length, one dict {network: next hop} per length (7 lengths in this table), and a lookup tries the longest length first and stops at the first hit. Memory is one dict entry per route (5,000 entries) plus a tiny tuple per length; a bit-by-bit trie of the same table needed 52,862 nodes, about ten times more.
- R5: the lookup time is now proportional to the number of distinct prefix lengths in the table (at most 33, here 7), not to the number of routes, and each probe is one hash lookup. A packet that falls inside a /24 is answered after one probe; one that matches only the default route pays for all 7. The measured speedup over the linear table was well over 1000x and every one of the 20,000 answers matched (the exact figure is in out/bench.txt).
- The bit-walk is what hardware builds because its cost is fixed and tiny per step: always at most 32 steps, each one a single memory read of a node that can be pipelined one level per clock, with no hashing and no collisions. In Python it loses: I measured a bit trie at roughly four times slower than the per-length dicts, because 32 interpreted steps cost more than at most 7 hash probes done in C. So the fast answer in Python and the answer hardware uses are different answers.
